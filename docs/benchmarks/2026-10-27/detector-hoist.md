# IFMA detector snapshot: evidence and reconsideration conditions

Status: **not implemented or performance-qualified**. Ordinary generic x86 assembly proves that the NTT short fallback still reads cached CPU-detector state. The internal threshold tuning atomic already folds in a normal consumer. This proposal targets the remaining detector accesses, not an assumed atomic at every scalar multiplication.

The [prior threshold-state experiment](../decisions/README.md) was completed and remains unmerged, with no established overall benefit. Its retained candidate already stored a captured Karatsuba threshold in `Ntt`, used it for the short fallback and threaded it through free NTT recursion. Since `ifma_threshold()` also tests CPU availability, that candidate addressed detector loads as well as the mutable tuning load. The current-source assembly finding does not establish that the old trial missed this path.

The old internal-worker and ordinary no-LTO outcomes differed. The ordinary consumer already folded the tuning atomic, and the [ordinary results](../decisions/threshold-snapshot/ordinary-no-lto-summary.csv) observed decoder costs about 20.5% higher at 4 KiB, 15.2% at 8 KiB and 6.2% at 64 KiB in that historical campaign. Those are old-source descriptive comparisons. Later [identical-file controls](observer-controls/README.md) limit causal attribution from comparisons of separate artifacts. These observations do not prove that state plumbing caused a slowdown or justify merging it.

The current observation separates two things that must not be conflated: a mutable internal tuning atomic that folds, and ordinary cached CPU-feature reads that remain. Both were implicated by the old getter; their distinction alone is not a new optimization. A genuinely narrower follow-up would reuse the value already computed by the **current** `Ntt::new`, after public length dispatch selects NTT, without changing all Karatsuba constructors or adding earlier detection. It still overlaps the old experiment and must earn a new ordinary-consumer win rather than inherit an internal-worker result.

Use the frozen `4e5ac883…` source and the ordinary Auto artifact contracts in [assembly.md](assembly.md) as the baseline. Keep the experiment separate from the accepted owned-capacity/empty-path changes.

1. Preserve the current high-level length/zero-prefix dispatch. Empty, tiny, batched and fixed-width paths must not acquire a new unconditional CPU-detector read or construct a multiplier merely to capture state. `Ntt::new` already calls `mul::ifma_threshold()` after NTT is selected; only there consider retaining the actual scalar threshold alongside its existing transform thresholds.
2. Pass that snapshot to `mul::mul_with` in the NTT short fallback and through its own free `ntt::mul_with`, `split` and recursive block calls. Do not recreate the old broad Karatsuba-state migration. Compare the new emitted code with the old rejected candidate before claiming this narrower scope produces a materially different result.
3. Keep the checked IFMA primitive's availability test. A caller can deliberately force a positive threshold through internal hooks on an unsupported CPU; the current contract panics when an IFMA leaf would be used. Calling a target-feature routine without proving CPU support is invalid. A later private capability token could encode the proof, but it needs a separate audit; do not add unsafe code merely to remove a load.
4. Define test-hook semantics explicitly: set the threshold before constructing a converter. A converter would keep one snapshot for its lifetime. Existing code already snapshots the NTT threshold family, but the scalar fallback currently observes later atomic updates. Concurrent mutation is a benchmark hook, not a public configuration API; still test and document the changed snapshot boundary.

A `usize` field nominally adds 8 B on 64-bit and 4 B on 32-bit targets, but layout padding, moves and spills can change the actual cost. Measure `size_of::<Ntt>()`, affected frames, readonly/code sections and tiny/default paths. On M5 and Wasm the getter is constant zero; avoid adding an unmeasured cost to those targets. Do not scatter new cfg branches just to hide an unproven field cost.

Qualification should include the normal no-internals public tests with 512 property cases for default/std/cache, forced scalar/IFMA comparisons on capable hardware, unsupported forced-threshold panic coverage, poisoned exact scratch, squares, imbalanced operands and threshold boundaries. Re-run the affected arithmetic proofs and Miri paths if executable code changes.

Measure ordinary consumers with generic and native x86 settings, with and without std/cache, across tiny, medium and large inputs through 4 MiB. Retain actual detector instruction counts, linked code/data, stack prologues and the normal allocation controls. Local and GCP measurements with qualified identical-content controls remain prerequisites to merging. This narrower follow-up remains an unimplemented, unmeasured hypothesis; the compact-feature study does not test it. No performance gain or merge recommendation is claimed.
